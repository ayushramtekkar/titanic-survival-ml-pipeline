1. Introduction¶

Setting the scene. The scenario I've used for this assignment is that I've just joined a company that deals with travel insurance and maritime risk. My line manager wants to see whether it's technically feasible to build a model that can estimate, before a ship even leaves port, how likely a particular passenger is to survive if something goes wrong — using nothing but the information already on their booking. If this works, it opens the door to things like more accurate risk-based pricing, understanding which passenger profiles carry the most risk, and creating a reusable blueprint for similar prediction tasks elsewhere in the business (such as estimating claim likelihood).

The ML angle. Framed technically, this is a binary classification task. The output is either 1 (survived) or 0 (didn't survive). The features feeding into the model come from passenger records — things like the ticket class they booked, their gender, approximate age, how many relatives were on board, what they paid, and where they embarked.

Why the Titanic data makes sense here. What I find genuinely interesting about this dataset is that the outcomes weren't arbitrary — survival was tied to social factors in a way that's now well-documented. Eaton and Haas (1995) highlight how class and gender shaped who got onto lifeboats. That means a good model should be able to pick up on real, meaningful patterns rather than just memorising noise. It's also a useful testbed for going through the full supervised learning process from start to finish: patching up messy real-world data, building new features, testing different preprocessing approaches, optimising model settings, and presenting findings in a way that's honest about what they do and don't show.

Who this is useful for. On the business side, an interpretable model gives the insurance team something they can actually explain to clients or regulators. More broadly, having a clean end-to-end worked example is something I personally found valuable when learning this material, so I've tried to make it easy to follow.

4. Data Cleaning and Feature Engineering¶

Taking the EDA findings as a starting point, I made these decisions:

  • Removed three columns: PassengerId (meaningless for prediction), Cabin (too sparse to impute sensibly), and Ticket (high-cardinality free text with no obvious pattern).
  • Title extracted from Name: Rather than keeping the full name string, I pulled out the salutation — Mr, Mrs, Miss, Master, or grouped others as Rare. A title carries implicit information about gender, age group, and social rank, all packed into a single compact feature.
  • Family size derived from sibling/parent columns: FamilySize = SibSp + Parch + 1 collapses two related columns into one, capturing whether someone was travelling solo or in a group.
  • Imputation approach: Median value for Age (appropriate given its right-skewed distribution); most common value for Embarked (only two missing entries, so the choice barely matters).
  • Encoding: One-hot encoding applied to Sex, Embarked, and Title.
  • Scaling: StandardScaler on numeric features — whether this actually improves things is tested properly in the next section rather than just assumed.

All of this is implemented through scikit-learn transformers so it can live inside a Pipeline and be applied consistently without leaking information from the test set.

In [ ]:
def engineer_features(data):
    data = data.copy()
    data["Title"] = data["Name"].str.extract(r",\s*([^\.]+)\.")
    rare_titles = data["Title"].value_counts()[data["Title"].value_counts() < 10].index
    data["Title"] = data["Title"].replace(rare_titles, "Rare")
    data["FamilySize"] = data["SibSp"] + data["Parch"] + 1
    data = data.drop(columns=["PassengerId", "Name", "Ticket", "Cabin", "SibSp", "Parch"])
    return data

from sklearn.pipeline import Pipeline
from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler, OneHotEncoder

numeric_features = ["Age", "Fare", "FamilySize", "Pclass"]
categorical_features = ["Sex", "Embarked", "Title"]

numeric_pipeline = Pipeline(steps=[
    ("imputer", SimpleImputer(strategy="median")),
    ("scaler", StandardScaler()),
])

categorical_pipeline = Pipeline(steps=[
    ("imputer", SimpleImputer(strategy="most_frequent")),
    ("encoder", OneHotEncoder(handle_unknown="ignore")),
])

preprocessor_scaled = ColumnTransformer(transformers=[
    ("num", numeric_pipeline, numeric_features),

])

5. Data Engineering Comparison¶

I didn't want to just assume that scaling would help — I wanted to actually check. To do that, I ran the same default Logistic Regression model under two different preprocessing setups, using 5-fold cross-validated accuracy as the yardstick. Logistic Regression was a good choice for this test because it's one of the algorithms that's genuinely sensitive to feature scale, so any difference should show up clearly.

  • Setup A: Imputation and one-hot encoding, but no scaling.
  • Setup B: Same as above, with StandardScaler added for the numeric columns.

Setup B won, which is what I expected. The reason scaling helps here is that the optimiser trying to find the best Logistic Regression coefficients works more efficiently when all the inputs are on a similar scale — it's not having to make enormous steps in one direction (for Fare) and tiny steps in another (for Age). The regularisation term also distributes more fairly across all features when they're scaled. From this point on, Setup B is the standard preprocessing for all models. Technically, trees like Random Forest don't benefit from scaling at all — but using one consistent pipeline for everything is simpler and doesn't hurt the forest.

6.2 Candidate models¶

I picked two approaches that sit at quite different ends of the complexity spectrum:

  • Logistic Regression — This one models survival probability as a sigmoid function of a linear combination of the inputs. The big advantages are speed, low memory footprint, and direct interpretability — you can read the coefficients and see exactly which features push the prediction up or down, and by how much. The limitation is that it assumes a roughly linear boundary between classes, so it may underperform when interactions between features matter a lot.
  • Random Forest — Rather than a single model, this is an ensemble: dozens or hundreds of decision trees, each grown on a bootstrapped sample and restricted to a random subset of features at each split. The aggregated prediction is more stable and handles non-linear relationships naturally. The trade-off is that there's no single simple explanation you can give for a prediction, and there are more knobs to turn during tuning.

6.3 Pipelines¶

Each model is embedded in a Pipeline alongside the preprocessing transformer. The key benefit here is that during cross-validation, the imputer and scaler only ever fit on the training fold — they never see the held-out portion. This eliminates a common source of data leakage that can make models look better than they actually are.

7. Hyperparameter Tuning¶

Running either model with default settings isn't usually the best you can do. I used GridSearchCV (5-fold CV, optimising for accuracy) to search across the most impactful settings for each one:

  • Logistic Regression — C: This controls how strongly the model's weights are penalised. A small C keeps the model conservative and constrained; a large C gives it freedom to fit the training data more aggressively. Getting this wrong in either direction costs performance.
  • Random Forest — n_estimators and max_depth: The first controls how many trees are in the ensemble (more trees = more stable, but diminishing returns). The second limits how deeply each tree can grow — unconstrained trees tend to overfit by memorising individual training examples rather than learning general patterns.

The grid search results told a fairly clean story. For Logistic Regression, very tight regularisation (tiny C) hurt the score a bit, but beyond a certain point the accuracy flattened out — there's a range where the model is well-calibrated and pushing further doesn't help. For Random Forest, the max depth story was stark: fully unconstrained trees did noticeably worse because they overfitted the training folds. Keeping depth at four to eight levels hit the sweet spot between model flexibility and generalisation. Adding more trees beyond a certain point mainly reduced noise in the score without moving the average much. The winning settings from each search were kept for the final test set evaluation.

8. Final Evaluation¶

With both models tuned, it was time to run them against the test set — the 20% that hadn't been touched at any stage of training or hyperparameter search. This is the evaluation that actually matters.

Given the class imbalance and the fact that both kinds of prediction error have real costs in this business context (over-estimating risk means overcharging customers; under-estimating it means financial losses), I didn't rely on accuracy alone. F1-score was the headline metric, supported by precision, recall, and AUC.

9. Conclusion¶

Summary. This notebook walked through the full supervised learning workflow on the Titanic dataset — from raw data to a tuned, evaluated pipeline. The preprocessing comparison in Section 5 gave empirical backing to the decision to use StandardScaler. Both Logistic Regression and Random Forest were tuned using grid search and then tested on a clean held-out set.

Which model won, and why. Logistic Regression came out on top across the main metrics — accuracy, F1, and AUC. Given the dataset size and the relatively linear nature of the survival signal, that result makes sense. It's also the model that's easier to explain, which matters in a context where you'd need to justify decisions to non-technical colleagues or clients. The Random Forest isn't far behind and could potentially close the gap with richer features or more data.

What drives predictions. Gender, passenger class, and title were consistently the most influential inputs — a finding that holds up across both the EDA and the coefficient analysis.

Can we explain the predictions? For Logistic Regression, yes — the coefficients do that job directly. For the Random Forest, explanation would require additional tools like SHAP or permutation importance, which weren't computed here but would be a natural extension.

Honest limitations. A dataset of 891 rows from a specific disaster over a hundred years ago has obvious constraints. The learned associations probably don't transfer well to modern maritime contexts. The test set of 179 examples is small enough that performance differences between models could shift with a different random split. Imputing age from the global median is a crude approach — grouping by title or class would likely give better estimates.

Extensions worth trying. Some ideas for future work: extracting cabin deck information from the partially available Cabin column; adding a feature for solo versus group travel based on ticket numbers; trying Gradient Boosting or SVMs; replacing the fixed grid search with a randomised search over a broader parameter space; and using repeated stratified cross-validation for more robust performance estimates.

Deployment verdict. I wouldn't deploy this as an automated decision-making tool. The dataset is too small and too historically specific, and the margin between models is sensitive to how the data is split. The right role for this would be as a reference tool to assist human judgement — not to replace it.
